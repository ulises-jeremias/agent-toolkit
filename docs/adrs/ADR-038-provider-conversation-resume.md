# ADR-038 — Provider conversation ids on PersonSession records and GUI resume

- **Status:** Accepted (2026-10-21); implemented in `apps/desktop/src/features/people/providerResume.ts`, `apps/desktop/electron/provider-session-capture.ts`, `modules/agent_toolkit_core/sessions.v`
- **Deciders:** ulises-jeremias (owner)
- **Builds on:** ADR-037 (detached PTY host), ADR-036 (durable People)

## Context

Person sessions ended with the PTY: even when the underlying runner
(claude, codex, copilot) keeps a durable conversation, Agent Toolkit did
not record its id, so "start again" in the People UI always opened a
fresh conversation and honestly said so. ADR-036/PEOPLE.md listed
provider session ids and safe resume as a gap.

Facts verified against the locally installed CLIs (`--help` output,
2026-10-21):

- claude: accepts an assigned `--session-id <uuid>` at launch;
  `--resume <id>` continues it.
- copilot: `--session-id <id>` sets or resumes a session UUID.
- codex: `codex resume <id>` exists, but the id is generated by Codex and
  recorded in `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-*.jsonl`
  (`session_meta` first line with `id` + `cwd`). It cannot be assigned.
- opencode: session ids are timestamp-encoded (`ses_...`); `--session`
  can create-or-continue but a fabricated id is not safe. Its session
  store (server/DB) is not a stable Desktop contract yet.
- gemini: no local CLI to verify a dialect against.

## Options

### 1. Only "restart with same settings" (status quo)

- Pros: zero risk.
- Cons: leaves the core Munder-style continuity feature unimplemented.

### 2. Typed dialect registry with assign/capture strategies (chosen)

Each runner gets an explicit strategy — `assign` (we choose the id),
`capture` (the PTY host discovers the id the runner recorded), or
unsupported (no guessing). The id lives on the durable V `PersonSession`
record; resuming starts a **new** PTY and a **new** record that carries
the same provider conversation id.

### 3. Parse every runner's private storage from the renderer

- Cons: couples the UI to unstable on-disk formats, duplicates work per
  runner, and bypasses the engine's authority over session records.

## Decision

Adopt option 2.

- **Record**: `PersonSession.provider_session_id` (V core) is the single
  source of truth. It is set at create time for assign-strategy launches
  (`POST /api/v1/sessions`) or attached once after spawn for capture
  (`POST /api/v1/sessions/:id/provider-session`, write-once: a different
  second id is a 409 conflict, never an overwrite). Ids are validated as
  opaque transport-safe tokens (1–128 chars, `[A-Za-z0-9_-]`, never
  interpreted, executed or used as a path).
- **Dialects** (`providerResume.ts`): claude/copilot = assign
  (`--session-id <uuid>` at launch, `--resume <id>` / `--session-id <id>`
  to resume); codex = capture (resume via `codex resume <id>`, no model
  flag is invented for it); opencode/gemini/unknown = unsupported and the
  UI states that plainly.
- **Capture** (`provider-session-capture.ts`, run by the PTY host after
  spawning a codex PTY): only rollout files modified inside the spawn
  window whose recorded `cwd` equals the PTY cwd are accepted; "newest
  overall" is never guessed. The host stores the id on the session,
  broadcasts `provider-session`, and the renderer attaches it to the V
  record (on capture and again during startup reconciliation).
- **GUI**: the Person Start dialog shows conversation continuity
  explicitly — a "Continue the previous conversation" toggle when the
  previous record is resumable with the selected runner, and an honest
  note when it is not. Unchecking starts fresh and leaves the previous
  conversation untouched.

## Consequences

- People sessions for claude, copilot and codex can be genuinely resumed
  from the Desktop; process continuity across app exit comes from
  ADR-037, conversation continuity from this ADR.
- A resumed conversation produces a new `PersonSession` record; history
  stays a chain of records sharing one provider conversation id, not a
  mutated record.
- opencode/gemini resume remains a documented gap pending a stable,
  verified capture surface; adding a runner means extending the dialect
  registry plus tests, not touching the record model.

## Rollback

Remove `provider_session_id` handling (records keep the field as inert
data), the attach route, the capture module and the dialog toggle. No
user conversations are affected; runners keep their own storage.
