# ADR-027 — Server/core boundary: thin HTTP adapter

- **Status:** Accepted (2026-08-23)
- **Deciders:** maintainer
- **Related issues:** #492, epic #830, proposal v2 (`/home/ulisesjcf/.opencode/plan/server-proposal-v2.md`)

## Context

EPIC 14 (#471) requires an HTTP surface so Web UI (#472), remote clients and CI agents can use the toolkit. The CLI already wraps a pure core (`agent_toolkit_core`). We must decide where HTTP logic lives.

## Options considered

1. **Fat server** — server owns workflows, parses YAML, mutates FS itself.
   - Rejected: duplicates domain logic; drifts from CLI; hard to test.
2. **gRPC service** — efficient binary protocol.
   - Rejected: browser friction (needs proxy), protoc toolchain, overkill for our scale; SSE covers streaming needs (already used in `trace.jsonl`).
3. **Thin adapter (chosen)** — `agent_toolkit_server/` maps HTTP ↔ core 1:1. Router generated from `cli-contract.yaml`. No business logic in handlers.

## Decision

New module `modules/agent_toolkit_server/`:

- `server.v` — net.http listener + graceful shutdown
- `router.v` — table generated by `scripts/generate_surface.py` from the contract
- `middleware.v` — auth (bearer for remote), CORS allowlist, logging
- `jobs.v` — process-per-run supervisor (ADR-020 semantics) exposing SSE events
- `sse.v`, `policy.v`

Core stays dependency-free (no `net.http`). Server is excluded-able in minimal builds but shipped in the standard binary as subcommand `serve`.

## Consequences

+ One implementation of every capability (parity enforced).
+ Core remains pure and unit-testable.
− HTTP handler code is boilerplate-y; mitigated by codegen.

## Validation plan

- `tests/test_surface_parity.py` — contract↔OpenAPI parity.
- `agent-toolkit serve selfcheck` — runtime diff of routes vs contract (Required CI after Phase 5).
- Integration: schedule loop via HTTP produces identical artifact to CLI (#729 emitter).
